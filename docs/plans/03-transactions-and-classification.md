## 2. Confirmed decisions and constraints

### Product authority retained

- The actors are the current verified subscriber operating only their own workspace, the trusted Next.js server, and the independently authorizing backend. Admin privileges confer no financial access to another customer.
- One non-null category points to the customer's real category row. Clearing means assigning their system Uncategorised row, never `NULL` or a new bucket. Tags are independent, zero-to-many labels.
- Imported date, description, signed amount, account, statement/source and duplicate identity never change here. Only category, tag links and `is_hidden_by_user` can change. No individual delete action, endpoint, export or workaround.
- Archived accounts remain readable/filterable and their historical transactions remain editable. Archived categories/tags remain visible and searchable on history; they are not new assignment choices. Archived tags can be removed. Category/tag lifecycle management stays in Settings.
- Hidden means `statement_imports.is_hidden OR transactions.is_hidden_by_user`. Transfer, Excluded, Uncategorised, Untagged and zero-value rows remain visible unless actually hidden. Direction follows amount sign, not category kind.
- Tag suggestions require an explicit confirmation. They may use explicit customer aliases, the customer's own historical choices for a generic merchant key, and exact/truncated-prefix token matching; there is no external merchant directory, cross-customer learning, automatic rule application or auto-categorisation. Category suggestions are advisory and detail-only.
- Privacy covers descriptions, amounts, account/institution/category/tag names, search text, statement content and filenames. None enters URLs, application logs, audit payloads, browser storage or analytics. IDs, fixed action/status codes and counts may be logged. Keep all backend secrets/tokens server-only.

### Architecture decisions for this unit

1. **One backend query definition.** A typed, allowlisted filter model and parameterized predicate builder supplies list rows, matching counts and filter-wide selection. Tags use `EXISTS`, not multiplying joins. The frontend does not fetch all rows and filter them locally.
2. **Body-based search.** `POST /v1/finance/transactions/query` carries private search text. The frontend calls it through an authenticated Server Action. Nonsensitive IDs/enums/date/page choices may be in `/transactions` links. Search stays only in component memory and request bodies, never query strings or persisted browser history/storage.
3. **Optimistic transaction versions.** List/detail expose the existing transaction `version`. Every real metadata change increments it exactly once per changed transaction, regardless of how many fields change. No-op requests with a current version leave it unchanged. Always check version before considering a no-op; an old request cannot bypass conflict by proposing the current value.
4. **Atomic bulk snapshot, not a moving query.** Preparation captures exact IDs and versions plus the chosen action. Filter-wide selection is every match in one database snapshot at preparation, not the current page, and not an open-ended subscription to future matches. Later imports are not selected. The confirmation states the capture time and this boundary. Never re-run a query at apply time to silently substitute a different set.
5. **No silent partial save.** If any selected transaction changed/disappeared, a target became unavailable/changed, a tag limit would be exceeded, or the selection expired, apply changes no selected transaction. The user refreshes and prepares a new confirmation. Do not retry against refreshed versions automatically.
6. **Durable bulk recovery.** A saved operation owns a manifest and immutable action. Applying it writes effects and a compact receipt in the same transaction. Retry/status after process restart returns the same result, even if those transactions are subsequently deleted by a statement deletion. It never replays the effects.
7. **Parent hiding wins.** Individual restore never restores a statement. If any selected transaction has a hidden parent, a restore request fails atomically with `parent_hidden` (or a stale-version conflict if that transition occurred since preparation). Link to the owned statement in Imports. Restore the parent there first, preserving individual flags, then prepare an individual/bulk restore. Classification of hidden rows is allowed.
8. **No reporting implementation.** In this Plan, “filtered total” means a transaction **count**. Do not introduce Money in/out/Net, category/tag money totals, coverage percentages or hidden monetary summaries. Row amounts remain exact and available for later reconciliation. Thread #5 owns calculated financial summaries.
9. **Prevent framework argument logging before action execution.** In `frontend/next.config.ts`, set only `logging.serverFunctions` to `false` using the existing Next.js 16.4.3 option. This disables development invocation lines for all Server Functions, including transaction and existing non-transaction Server Actions. The framework captures arguments before action authentication/validation and retains them on success or failure; an action-local sanitizer is not the privacy boundary. Keep incoming-request logging, existing fetch/browser logging settings, application diagnostics and backend `audit.*` events unchanged. Do not use `logging: false`, suppress console output, scrub captured logs after the fact, change action transport, or patch dependencies. The production invocation path already excludes this development-only logger; no production logging/authorization policy change is proposed.

10. **Credential-bound session issuance (revision 3, W1).** Serialize the exact verified-hash comparison and session insert through commit against password reset. The existing freshly salted hash is sufficient credential identity; no schema addition is authorized. Section 6.6 defines the denial and reset barriers.
11. **Truthful account preflight (revision 3, M4).** Permit a dedicated typed account-read error in the shared server client, preserving its success/throw interface. Only transaction routes adopt non-revoking outage/rate-limit states. Section 6.7 defines the boundary; unrelated callers retain existing behavior.

These are technical decisions in the approved Plan, not claims that the operator chose every implementation technique. Assumptions: a typical personal workspace fits the bounded synchronous operations below; public service-level objectives remain unvalidated. No unresolved product decision requires an implementation agent to invent architecture. Revision 3's bounded execution is explicitly approved; publication and deployment remain unauthorized.

## 4. Invariants and target architecture

1. **Single owner and source of truth.** Every query, manifest, mutation, tag link and operation is scoped to the authenticated customer. Foreign and unknown IDs have the same `404 {"error":"not_found"}`; a mixed owned/foreign selection fails wholly. Same-customer database constraints remain. No request takes `customer_id` as authority.
2. **Immutable financial source.** No new write statement updates source/identity columns or deletes a transaction. Unknown/forbidden fields are rejected, not ignored. ZAR amounts travel as invariant decimal strings with two fractional digits; C# decimal/PostgreSQL numeric or integer cents handle values. Never parse financial amounts into JavaScript floating-point numbers, including sorting/display formatting. Preserve zero and the `NUMERIC(18,2)` extrema; normalize negative zero to zero without changing stored money.
3. **Truthful visibility.** All transaction query/selection visibility uses the common parent-OR-individual predicate. A parent transition increments child versions as today. Child operations never change parent flags, statement version, historical import counts, account `import_version`, fingerprints, occurrences or import receipts. Dynamic hidden counts in Imports reflect the actual child flags on the next read.
4. **No lost metadata.** Check and lock the expected transaction versions. A changed category ID, tag assignment or individual flag, category/tag deletion, or parent visibility change invalidates a stale edit. One conflict rolls back the entire bulk operation, including all tag links and receipt writes. Suggestions are never a write path by themselves.
5. **Non-destructive tag algebra.** Final tags are `(existing tags UNION add_tag_ids) MINUS remove_tag_ids`. Reject overlap between add/remove inputs. Unrelated tags and category are preserved unless explicitly changed. Existing archived assignments survive unrelated edits. No replace-all contract exists. To clear all tags, the detail UI explicitly removes the currently assigned IDs under the transaction version check.
6. **Exact scope and counts.** A bulk manifest contains every captured match exactly once. Never silently truncate to a page, limit or successfully updated subset. `selected_count = changed_count + unchanged_count`. The receipt reports row changes, not the number of field or join-row writes. Counts describe the operation's committed effect, not a later view of the dataset.
7. **Terminal recovery.** Applied, Abandoned and Expired operation IDs never become Prepared again. An applied receipt is checked before expiry/member validation. Abandon after apply returns the applied result, not an undo. A deleted parent cannot be resurrected through a saved operation.
8. **Private transport and evidence.** All transaction responses, including failures, are no-store. Server actions authenticate independently of page checks. Errors and database exceptions never echo bodies, SQL values or sensitive content. Test fixtures/evidence use synthetic data only.

Use `backend/Transactions/` for filter/action/limit/contracts, `backend/Finance/` for the shared merchant-key, alias/history and tag-token suggestion helpers, `Data/TransactionStore.cs` for owned persistence, and `Http/TransactionEndpoints.cs` for guarded transport. Do not add transaction behaviour to the already large import store. The shared suggestion helpers are consumed by both import review and transaction detail; preserve import behavior and test both consumers in the same change.

## 6. Data/control flow and lifecycle

### 6.1 Query, inventory and pagination

The query body has `filters`, `page`, `page_size`, `sort_by`, `sort_direction`. `filters` accepts only:

- `search`: optional trimmed literal substring, at most 200 Unicode scalars; empty means absent. Case-insensitive match against the preserved description **or** any assigned tag display name, including archived tags. Escape SQL wildcard characters `%`, `_` and backslash; do not interpret regular expressions, token rules or merchant normalization. The whole string is one substring, not an implicit OR of words.
- `start_date`, `end_date`: optional independent inclusive ISO calendar bounds; reject invalid dates and start after end. No timezone shift, automatic latest-month restriction or invented default period; absent bounds mean all dates.
- `financial_account_id`, `statement_import_id`, `category_id`: optional single UUIDs. Resolve each as owned before returning rows/counts. An owned account/statement mismatch is simply zero matches. Archived accounts/categories are valid history filters. The Uncategorised shortcut uses the actual system category ID.
- `merchant_tag`: absent, one owned UUID, or `untagged`. It cannot be both a tag and Untagged or contain a list. Untagged means **no links at all**, including archived tag links. Search and this filter are ANDed, as are all filter dimensions.
- `category_kind`: absent or `Income`, `Expense`, `Transfer`, `Excluded`, `Uncategorised`. A conflicting category/kind combination yields zero matches, not an altered filter.
- `direction`: absent or `in`, `out`, `zero`, respectively amount greater than, less than, or equal to zero.
- `visibility`: `visible` (default), `hidden`, or `all`. Hidden includes parent-only, individual-only and both, once per row.

`sort_by` is `date` (default), `amount` or `description`; `sort_direction` is `desc` (default) or `asc`. Amount order is numeric in PostgreSQL, not lexicographic. Description order is the database's deterministic text order for the deployment; every order appends transaction UUID in the same direction as a unique tie-breaker. Page is a positive integer; page size is 25 by default and one of 25/50/100. Reject malformed/unknown fields/enums, duplicate singleton URL parameters, invalid sizes and overflow; do not broaden invalid filters into “all.” An out-of-range valid page returns no rows with the accurate counts.

Return rows and these counts from one read-only repeatable-read database snapshot (or one SQL statement with the same snapshot guarantee):

- `inventory_count`: all owned committed transactions, ignoring every filter, including hidden and archived-account history. No reviews, suppressed incoming rows, deleted statements or foreign rows.
- `matching_visible_count` and `matching_hidden_count`: apply every filter **except visibility**, counting by the common effective-hidden predicate.
- `matching_total`: the sum of those two counts.
- `filtered_total`: apply visibility as well; this is the pagination/“all matching” count. Visible selects the visible count, Hidden selects the hidden count, All selects their sum.

The UI says, for example, “120 visible and 8 hidden match these filters; showing 120 visible.” The Hidden tab preserves the other filters and shows the hidden subset. Never label a page count as the total. `inventory_count = 0` means first import needed; positive inventory but no filtered rows means no matches, all matching rows hidden, or an empty page—not no finance data. If visible count is zero but hidden matches exist, offer the Hidden view. Counts are inventory, not amount sums or reporting denominators. Settings' existing all-state assignment counts and Imports' historical counts retain their existing meaning.

Use parameterized SQL with owner predicates on every relation, `EXISTS` for tag search/filter and a bounded aggregate fetch for tags on returned rows. Avoid one query per row. List rows contain the fields in Section 8; detail adds suggestions and source position. No source identity discriminator, fingerprint, raw upload content or filename is returned.

Pagination is a live view, not a lasting dataset snapshot across separate requests. Concurrent edits/imports can move rows between pages; refresh to reconcile. Preserve checked explicit IDs/versions across page navigation, never silently replace them by row position. Changing filters, search, sort or page size clears selection and any prepared confirmation; changing only page preserves selection. Ignore late asynchronous responses from an older query generation. Failed/incomplete inventory or taxonomy loads disable affected controls with a retry state; never substitute successful zero counts or an empty category/tag set.

### 6.2 Single edit, inline/detail controls and suggestions

An inline or detail save sends `expected_version` and a bounded `changes` object. All submitted fields are applied together or none are. Omitted fields preserve existing state. `category_id` is an owned active category (the system row is valid), not null. `add_tag_ids`/`remove_tag_ids` are distinct UUID arrays, disjoint, at most 100 each. Adds require active owned tags; removes permit archived owned tags. Reject unknown/foreign IDs even when removal would be a no-op. The resulting set may have at most 100 tags; an edit with no adds may reduce a legacy oversized set without first forcing unrelated removals.

`is_hidden_by_user` is an optional boolean. Hide/restore requires `confirm: true`, with count 1 and the read-only transaction identity shown in the UI. Parent-hidden restoration follows Section 2. Other metadata saves use an explicit Save action but need not add a second modal. No automatic assignment follows opening detail, choosing a filter, focusing a field or receiving suggestions.

Suggestions combine three advisory sources: the customer's explicit aliases, the customer's own historical tag/category choices for the generic merchant key, and active owned tag-name token matching. Aliases resolve to one active owned tag and an optional active owned non-system category. History uses only the customer's committed transactions, grouped by the generic merchant key; only active owned tags and the most frequent active non-system category are eligible. Token matching accepts exact contiguous tokens first, then a statement token that is a truncated prefix of a longer tag token (minimum four characters, tag token at least five); a longer statement token never shortens to a tag token. Compose aliases, history, then token matches; deduplicate and exclude already assigned tags. Return up to 20 deterministic suggestions plus `has_more_suggestions`. Detail may also return one optional `suggested_category` from the first matched alias category or the history category. Suggestions are never assignments: a tag chip sends the explicit add-tag mutation with the displayed transaction version; a category suggestion is offered only for an Uncategorised transaction, stages the category in the form, and is saved only by the explicit Save action. Ignoring either changes no finance data. A renamed/archived/deleted tag or category is refreshed/revalidated; it is never silently replaced by a different ID. There is no page-wide suggestion scan and no automatic assignment.

The backend resolves the owned transaction's immutable account ID, acquires the locks below, rereads and compares the version, then validates and writes only changed metadata. A stale request returns `409 version_conflict` with no finance effects. A deleted/foreign transaction returns the same 404. Return a fresh transaction DTO after success. On an uncertain single-save response, fetch the fresh detail and explain that the outcome was uncertain; never issue the old intent with a newly fetched version automatically. A retry with the original version either encounters the unchanged row or conflicts; it cannot overwrite a later change.

### 6.3 Bulk selection, preparation and confirmation

Two selection modes:

1. `explicit`: `{id, expected_version}` tuples checked individually or by “Select this page.” The checkbox selects exactly the loaded page's rows. Preserve tuples across pages; deduplicate client selections, but reject duplicate tuples/IDs in the public request. Maximum 1,000 explicit rows; offer all-matching or narrowing rather than quietly dropping extras.
2. `all_matching`: the same canonical `filters` as the list, including visibility, with **no page or sort restriction**. Preparation evaluates the complete predicate in one snapshot, up to 50,000 rows. Above that bound reject `selection_too_large` and request narrower filters. At the bound select all 50,000, not 49,999. Never split into partially committed chunks.

The client supplies a fresh UUID `operation_id` once per intended preparation, `selection`, and `changes` using the single-edit algebra. At most five nonexpired Prepared operations and 100,000 total live manifest entries per customer; quota check and insertion serialize on the customer row. Prepared operations expire after 15 minutes, absolute. Preparations are additionally bounded at 20 per customer per 15 minutes; ordinary finance limits still apply. Query JSON is bounded to 16 KiB; edit/preparation/confirmation bodies to 256 KiB, checked by actual read length even when Content-Length is absent/false. Do not raise Next.js's current action body limit: explicit selection fits below it and all-matching sends only a filter.

Preparation makes no transaction/category/tag/statement changes. Use a serializable database transaction for quota checks and snapshot capture; a snapshot taken before waiting on a customer lock must not miss another preparation's inserted manifests and exceed the quota. Serialization failure rolls back the whole preparation and is safely retryable with the original operation ID. In that snapshot validate ownership/input, match or check versions, capture members and action targets, compute `selected_count`, prospective `changed_count`/`unchanged_count`, and check restore/tag-limit eligibility. Zero members returns `empty_selection`, not a successful operation. For explicit mode a stale tuple fails preparation rather than capturing its new version. Check an existing owned operation/digest before quota and recapture checks; concurrent identical preparations converge on that one operation, while differing payloads conflict.

The saved manifest contains IDs, immutable account/statement references and versions, not descriptions/amounts/tag names. Store only a canonical request digest and filter digest—not plaintext search text—for request replay and scope identity. Persist the action's IDs and target revision stamps while Prepared. A confirmation hash covers owner, operation ID, manifest, action, target revisions, counts and expiry. A digest/hash is a consistency check, not a bearer authorization token. Store-owned records and session ownership remain authority.

The response shows capture/expiry time, selection mode, exact selected/changed/unchanged counts and the resolved category/tag choices. The UI combines it with the user's current filter chips. It says “N transactions selected across all pages as of [time]; later matches are not included; M will change and U already match.” Visibility changes state their exact scope and, for hide, that records and duplicate protection remain. Reconcile the selection banner to the fresh captured count; if it differs from the earlier list count, visibly explain the new count and require confirmation of that updated scope. Clear selection is always reachable. Cancelling confirmation does not write transaction data.

### 6.4 Apply, lock order, concurrency and recovery

Apply sends only the saved operation ID, `confirmation_hash`, `expected_selected_count` and `confirm: true`. It cannot change the action or supply replacement members. Verify owner and confirmation inputs. If already Applied, return the stored counts/result with `replayed: true` before checking expiry, member existence or current target availability. A differing confirmation cannot reuse the operation.

For a Prepared operation: read its immutable account-ID list, lock those owned accounts in ascending UUID order, then lock/recheck the operation header. Recheck terminal state and expiry after waiting. Acquire classification locks, then lock all selected transaction rows by ascending UUID. Require the full manifest count and exact versions, revalidate targets and resulting tag limits, and then write the metadata, versions and receipt in one PostgreSQL transaction. No updated row, tag join, Applied state or receipt may survive a rollback independently.

The common write order is **accounts ascending → operation header (bulk only) → target category → referenced tags ascending → transactions ascending**. Use `FOR SHARE` for chosen category/tag rows so archive/rename/kind/delete cannot change their confirmed state during a write, while ordinary foreign-key key-share checks remain compatible. Acquire all such classification locks before any transaction/tag-link write. Lock both add and remove tag IDs; current unrelated assignments need not be locked as taxonomy resources. A bulk target changed in name/kind/archive/`updated_at` since preparation produces `classification_changed`, not a reinterpreted confirmation. Compare database timestamp precision without a JavaScript millisecond round-trip.

Do not acquire account/customer locks after holding transaction or classification locks. Keep category seeding outside these transactions; normal imported rows already have the seeded system category. Preserve the existing import order, receipt behaviour and category/tag public APIs. Mechanically adapt category and tag deletion in `FinanceStore` to lock their affected transaction IDs in ascending order before existing updates/removals. Their target-entity-first order remains, without adding account locks. Category reassignment's system-row foreign-key check must remain key-share compatible, not a newly introduced exclusive system-category lock. Statement operations already serialize on account rows and retain their present parent/child version behaviour. Race tests must exercise the actual paths, not only isolated SQL imitations.

At apply, deleted members or changed versions return `409 selection_stale`, with the count of stale/missing members and no partial result. Parent changes are caught by existing child-version increments. Changes to a taxonomy entity used only to select the frozen set do not redefine membership; the saved IDs remain the confirmed scope. New imports or other newly matching rows are not appended. Classification target changes, unlike those filter-only changes, invalidate the confirmation.

Use a five-second lock wait bound and a 30-second database statement bound on new workspace operations. Deadlock/serialization/lock-timeout failures roll back and map to safe `409 operation_busy`; a caller can retry the **same** still-valid operation. Do not change versions, automatically prepare a new set, swallow partial errors, or log exception Detail. Do not hold a database transaction open while the user considers confirmation.

Lifecycle: `Prepared → Applied | Abandoned | Expired`. A failed apply leaves Prepared until retry, abandon or expiry; it does not imply that any row changed. Process restart loads the same state from PostgreSQL. If cancellation/failure occurs before commit, roll back. A lost response or cancellation after durable commit leaves Applied and the same receipt. Status recovery distinguishes these states; the UI does not announce failure/no changes until it resolves an uncertain outcome. Abandon serializes on the operation header; if apply won, return Applied, not Abandoned. Repeated abandon on Abandoned succeeds without finance effects. Expired/Abandoned cannot apply.

Once preparation succeeds, retain its nonsensitive `operation_id` in the current `/transactions` URL for recovery after a page reload or backend restart. This is recovery state, not a filter or authorization. An uncertain prepare response can query status using the client-generated ID or retry the identical preparation. On reload, fetch status without applying anything: show an Applied receipt, explain a terminal refusal, or offer to abandon a still-Prepared operation and prepare afresh. Do not confirm a Prepared operation after losing its original private filter/action context. On a known Applied outcome, the client clears the operation identity and removes the recovery parameter without requiring a separate acknowledgement, shows a persistent status line with the changed/already-matched counts, clears the selection and prepared/recovery state, and refetches the list. The durable server receipt remains available for status/replay, so a reload that still holds the old operation ID can recover the Applied result. Abandoned and Expired outcomes retain their explicit terminal recovery. A client still holding the original confirmation may explicitly retry the same apply; it never substitutes a new version or operation ID to resolve uncertainty.

On apply/abandon/expiry, purge manifest and saved target/action detail, retaining only owner, operation ID, request/confirmation digests, terminal state, timestamps, action codes and historical counts. Terminal receipts do not reference live transactions/tags/statements through cascading foreign keys. Startup and 15-minute cleanup expire Prepared headers and remove payloads; handlers enforce expiry even if cleanup is delayed. Cleanup locks a header only and never then acquires accounts/customer locks. No new background-job system or raw financial history is introduced. Operation status/replay can therefore never recreate a later deleted transaction. Client auto-dismissal after an Applied outcome removes only the recovery identity; it does not delete or weaken the durable receipt.

### 6.6 Credential/reset barrier — W1, revision 3

Login currently verifies a detached customer hash, clears failures and inserts a session separately. Reset updates the hash and revokes existing sessions transactionally. The permitted old-hash read → reset commit → session insert ordering is unsafe. The two account source files are unchanged since initial commit `14ec505`; this is a bounded pre-existing defect, not a transaction regression.

- Bind issuance to the exact encoded hash successfully verified by the handler. The comparison and insert must serialize with reset's customer update through issuance commit, across backend processes. A snapshot-only conditional insert or process-local lock is insufficient. SQL technique is implementation-owned; no migration or credential-generation addition is required or permitted.
- If reset wins before issuance, return existing `401 invalid_credentials` with no session, success audit or success-only counter clear. Never accept a freshly read hash without verifying the supplied password against it. Preserve non-enumerating errors and existing wrong-password accounting.
- If issuance commits first, reset revokes that session before reset succeeds. A delayed login response may contain an already-revoked token; no token authorized by the replaced hash may authenticate after reset commits. Already-authorized application requests are not cancelled by this correction.
- Make successful-login counter clearing conditional on that same guarded issuance and transactional with it. Preserve verification/subscription checks, lockout policy, trusted-caller guards, token hashing, expiry and logout. Expensive password verification need not hold a database lock.
- Use customer credential row before session writes, compatible with reset's existing atomic token consumption/hash replacement/revocation. Cancellation/failure before commit rolls back session and success-counter effects. Return the token and log success only after issuance commits. Never log passwords, hashes or tokens.

### Backend HTTP contract

All paths below are under `/v1/finance`, snake_case JSON, through the unchanged trusted-caller/session/subscriber guard before body parsing. All responses are no-store. Reject unknown body/query properties and forbidden fields. UUID route paths never contain user names or descriptions.

| Method/path | Request | Success |
| --- | --- | --- |
| `POST /transactions/query` | Section 6.1 filter/page/sort body | `200` `{transactions, inventory_count, matching_visible_count, matching_hidden_count, matching_total, filtered_total, page, page_size, sort_by, sort_direction}`. Returned sort/page values are canonical. |
| `GET /transactions/{id}` | Owned transaction ID only | `200` `{transaction, suggested_tags, suggested_category, has_more_suggestions}`. `suggested_category` is null or `{id, display_name, kind, is_system, is_archived}`. Suggestions are not assignments. |
| `PATCH /transactions/{id}` | `{expected_version, changes, confirm?}` | `200` `{transaction, selected_count:1, changed_count, unchanged_count}`. |

| `GET /transactions/operations/{id}` | Owned operation ID | `200` safe status/summary and Applied receipt if present; no manifest dump or sensitive request content. `selection` is discriminated by `mode`: `explicit` carries `transactions:[{id,expected_version}]`; `all_matching` carries `filters`. Reject fields from both modes. `changes` has only optional `category_id`, `add_tag_ids`, `remove_tag_ids`, `is_hidden_by_user`; at least one real action field is required. Empty arrays alone are not an action. Supplying the same current category/state or adding an already assigned tag is a legitimate no-op after version/availability checks. The bulk apply's `confirm:true` confirms a hide/restore; preparation itself never changes flags.

The transaction DTO exposes: `id`, `version`, `transaction_date` (ISO date), preserved `description` (display fallback “No description” only when empty), exact `amount` string, `currency:"ZAR"`, `direction`, owned `financial_account:{id,display_name,is_archived}`, `category:{id,display_name,kind,is_system,is_archived}`, `merchant_tags:[{id,display_name,is_archived}]`, `statement_import:{id,statement_label,source_type,is_hidden}`, `is_hidden_by_user`, `effective_hidden`, `hidden_reason` (`none`, `individual`, `statement`, `both`). Detail additionally includes source row/page position and an optional advisory `suggested_category` (`{id, display_name, kind, is_system, is_archived}` or null). Tags have deterministic display-name/ID order. No normalized identity fields or raw source payloads are public. A category's kind never changes the sign/direction field.

Prepared summary exposes `operation_id`, `status`, `selection_mode`, `captured_at`, `expires_at`, `selected_count`, `changed_count`, `unchanged_count`, `confirmation_hash`, and resolved action choices for confirmation. The server stores no human-readable search summary; the client already has its current private search/filter text. Preparation digest equality is checked before recapture. Reuse of an ID with different content returns `409 idempotency_conflict`; identical preparation after terminal state returns that terminal summary and never creates a new operation.

Retain `401 unauthorized`, bodyless `403`, `404 not_found`, `429 rate_limited`, safe `500 internal_server_error`. New fixed codes: `400 invalid_request`, `empty_selection`, `category_unavailable`, `tag_unavailable`, `tag_limit_exceeded`, `selection_too_large`; `413 request_too_large`; `409 version_conflict`, `selection_stale`, `classification_changed`, `parent_hidden`, `idempotency_conflict`, `operation_busy`; `410 operation_expired`, `operation_abandoned`; `429 operation_quota`. Unknown/foreign selection members, filters, targets and operations use the identical 404. Stale error details may report owned conflict/blocked counts and a bounded list of owned statement links, never raw values or foreign IDs. GET status may return terminal Expired/Abandoned with 200 so recovery can display them; only apply rejects those states with 410.

## 12. Risks, compatibility, rollback and decisions

- **Snapshot expectations:** all-matching is exact at preparation, not forever. Capture time/count and the “later matches not included” warning are part of the public contract. Users deliberately prepare again to include new data. This avoids chasing a moving query or overwriting unseen changes.
- **Lock interactions:** entity deletion has a different established lock prefix from statement operations. This Plan uses shared target locks before ordered transaction locks and narrowly orders deletion rows; it does not solve this by changing import authority or globally locking all finance work. Real-path concurrency tests and bounded safe failure are required evidence.
- **Parent-hidden restore:** some Hidden rows cannot be made visible individually. Explicit refusal and the owned Imports link preserve parent authority and individual flags; do not relabel a zero-effect restore as successful restoration.
- **Content search cost:** literal substring search can scan a customer's dataset. Bounded pages, owner/date/amount indexes, existing finance limits, query timeouts and measured 20,000-row tests are the initial design. Trigram extensions, full-text services and background jobs require a later decision, not an unreviewed dependency.
- **Operational growth:** live manifests have finite quotas/expiry. Compact terminal headers intentionally remain for idempotency, without descriptions, names, amounts, filters or members. A new receipt-retention policy would change replay guarantees and requires a separate decision; do not silently delete terminal headers.
