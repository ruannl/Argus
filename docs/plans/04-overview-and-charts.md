### Decisions, assumptions and exclusions

**Operator decisions:** The default uses explicitly confirmed salary receipts, not a nominal monthly day or detected Salary category. One workspace-wide date sequence applies across account filters. The date survives source hiding/deletion; explicit removal/reselection is allowed after an impact warning. Same-date receipts share one boundary. The reporting date uses Africa/Johannesburg. Calendar last-three/six-month presets include the current partial month; shorter prior months clamp calendar month-to-date comparisons. Other merchant tags expand individually, without an aggregate amount or combined-tag filter. Custom dates means start/end dates only, not rolling N-day or duration controls. Layout A is selected.

**Technical choices in this draft:** Keep calculations on the backend, add two small customer-owned salary tables, extend the canonical transaction filter only as necessary for exact report drill-down, and draw accessible bars without a new chart dependency. Use uncached repeatable-read reporting responses rather than materialized totals or a reporting cache. These choices become execution authority only with acceptance of this Plan.

**Assumptions to measure:** The typical personal dataset is about 20,000 transactions. The brief's p95 under-two-second Overview response is a validation target, not an established service guarantee. No salary inference, future-payday knowledge or completeness of user-supplied statement periods is assumed. There is no unresolved salary-product choice after the same-date decision; an unforeseen contradiction stops the affected phase rather than silently changing meaning.

**In scope:** Receipt-based boundary management; period resolution; financial aggregation; statement coverage; all specified Summary/Charts/exploration views; exact same-filter list totals/links; narrow filter and read-query reuse; new-table migration/isolation integration; tests and operational documentation.

**Excluded:** Thread #11's navigation/Transactions/Imports/Settings visual refresh, PDF activation/hardening, parser/suggestion redesign, automatic salary detection, recurring-income detection, fixed payday/weekend/holiday adjustment, salary forecasts, manual boundary-date entry, per-account salary calendars, bank feeds, balances, budgets/advice, split transactions, FX, combined merchant-tag filters, individual transaction deletion, export/customer deletion, new packages, unrelated security/auth changes, deployment or publication. There is no fifth top-level destination.

## Invariants and authoritative data

1. **Authority is not a UI choice.** Every new API reuses `FinanceGuard` and passes `FinanceAuthority` into `CustomerDbScope`. Every protected relation has an explicit customer predicate as well as forced RLS. Unknown and foreign identifiers have identical `404 {"error":"not_found"}` behaviour. Admin privileges give no access to another customer's finance data.
2. **Financial source stays immutable.** No new write changes a source transaction, category, tag, statement, occurrence slot, import receipt or source identity. Salary confirmation stores a reporting date, not an inferred classification. Normal backend startup never migrates.
3. **Included means visible and not Transfer/Excluded.** Effective hidden is parent OR child. Positive included amounts form Money in; negative included amounts contribute their magnitude to Money out; Net is their difference. Income-category outflows and Expense-category refunds follow their sign. Uncategorised is included. Zero rows count but do not change value. Archived account/category/tag history is retained.
4. **Exact money is never binary floating point.** PostgreSQL numeric and C# decimal perform exact aggregation without pre-rounding. JSON amounts/deltas are invariant two-decimal strings, including sums larger than a single `numeric(18,2)` value. JavaScript uses string/BigInt cents for formatting and comparisons, never `Number`, `parseFloat` or locale parsing of money. Only a bounded, backend-computed display ratio may become a CSS number. An arithmetic/provider overflow fails the report safely; it never returns truncated, rounded or partial totals.
5. **Category and tag algebra differ.** Each included row has one category and appears in exactly one directional category bucket. Categories including Other and Uncategorised add exactly to that direction's headline. Each tag total counts a matching transaction once, but different tags may overlap. Tag coverage counts a tagged row once regardless of link count. There is no summed Other-tag bar.
6. **Two kinds of coverage are distinct.** Value coverage uses included absolute transaction value. Statement coverage uses the union of committed non-hidden statement dates for the selected one/all accounts, irrespective of category/tag filters or individual child hide flags. A retained salary date contributes no amount, transaction count or statement coverage.
7. **One response is one financial snapshot.** Current/comparison values, ranks, gaps, counts, detail rows and drill-down descriptors come from the same admitted repeatable-read context. Read responses are released only after its final authority check. Separate navigation requests are live views, not a frozen ledger; concurrent changes may require refresh.
8. **Privacy applies before execution and on failure.** No descriptions, amounts, names, search strings, raw files or salary receipt payloads enter URLs, storage/analytics or logs. Salary dates remain customer-owned reporting data; operational events log only IDs, status and counts. Retain existing `logging.serverFunctions: false` and EF logging suppression. Never log provider Detail, SQL values, bodies or a wrapped exception carrying them.

## Contracts and control flow

### Periods and comparisons

Use ISO `DateOnly` throughout backend period resolution. Resolve today once per request. Register .NET's built-in `TimeProvider.System` for a reporting-only clock, substitutable in tests, with no package or environment addition. If the required timezone cannot be resolved, fail reporting explicitly; never silently substitute UTC or browser-local dates.

The period request is exactly one of:

- `{mode:"salary_cycle", cycle_start_id?: UUID}`. Omission of the ID selects the latest confirmed start. No confirmed start returns `setup_required` with no invented dates or zero totals. An explicit missing/foreign/removed ID returns not_found, not the latest cycle. Resolve the selected start and its immediate successor/predecessors from the owned sequence. A successor closes the cycle on successor date minus one day; otherwise end at today. All starts are at or before today. Display the start/end and “Salary cycle” or “Salary cycle to date”; never suggest that a missing next receipt has been detected or that the open cycle is a normal-length month.
- `{mode:"calendar", preset:"month_to_date"|"previous_month"|"last_three_months"|"last_six_months"}`. Entering Calendar without a saved choice selects month-to-date. Last three/six starts on the first day two/five months before today's month and ends today, labelled partial. Additionally accept `{mode:"calendar", preset:"month", month:"YYYY-MM"}` for an explicitly selected full calendar month, including a future month when deliberately selected.
- `{mode:"custom", start_date:"YYYY-MM-DD", end_date:"YYYY-MM-DD"}`. Both dates are required and inclusive. Future ranges are allowed and have honest coverage/partial warnings. Do not add day-count controls.

Salary is the default when mode is absent; a URL-selected calendar/custom period is preserved on refresh/back navigation, not persisted as a new default. Neither account selection nor selecting a category/tag redefines salary boundaries.

| Selected period                | Comparison                                                                                                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Closed salary cycle            | Previous complete cycle bounded by the preceding confirmed start and selected start minus one day. Different lengths are allowed and shown.                                                      |
| Latest open salary cycle       | Same inclusive elapsed day count from the previous confirmed start, ending no later than the day before the current start. Explain a shorter prior cycle. One confirmed start has no comparison. |
| Full calendar month            | Previous full calendar month.                                                                                                                                                                    |
| Calendar month-to-date         | First day of prior month through min(today's day number, prior month end). Label same period last month and explain a shorter prior month.                                                       |
| Calendar multi-month or custom | Immediately preceding inclusive range of equal day length, ending the day before the selected start.                                                                                             |

Compute comparison dates from the period kind, not by guessing that arbitrary custom dates are a named month. Handle date arithmetic at years 0001/9999 without overflow: a range remains valid when its predecessor cannot be represented, but comparison is unavailable with a date-boundary reason. Always show exact ranges and partial/coverage state. No comparison appears when either period has no included rows or there are insufficient salary boundaries. Zero-valued included rows are data: absolute differences are valid but percentages are null when the prior metric is zero. Use `(current - prior) / abs(prior)` for a signed Net percentage, labelled relative to prior magnitude; ordinary nonnegative directional metrics use the same formula. Use neutral signed changes, not a judgement about financial health.

### Salary-date persistence and lifecycle

Migration ordinal **0012** adds:

- `salary_cycle_state`: `customer_id` primary key/FK to customers with ON DELETE CASCADE, `revision BIGINT NOT NULL CHECK (revision > 0)`, and `updated_at TIMESTAMPTZ NOT NULL`. No row means sequence revision `"0"`; the first new boundary creates revision 1. Serialize revision as a decimal string, not a JavaScript-unsafe integer. The state row remains after all boundaries are removed so an old sequence revision cannot become current again.
- `salary_cycle_starts`: `id UUID` primary key, `customer_id` FK to customers with ON DELETE CASCADE, `start_date DATE NOT NULL`, `created_at TIMESTAMPTZ NOT NULL`; unique `(customer_id,start_date)` and `(customer_id,id)`. Index/order by customer and date. Dates are immutable; correction is explicit removal and fresh receipt confirmation.

Persist **only the confirmed calendar date and its boundary ID/owner/timestamp**. Do not retain a receipt amount, description, account label, transaction payload, source locator or source FK. The transaction ID is a confirmation request input and is not saved in the boundary. This deliberately preserves a small independent date after statement deletion without an orphan transaction, retained source payload, or delete-blocking reference. Show this retention policy before confirmation and in boundary management. Calendar/custom reports do not need this table populated.

New guarded routes:

Validate duplicate/unknown query parameters and dates; return a next cursor, never truncate without one. No source payload is stored or returned by this list.                                                                       |

The receipt picker lives inside Overview setup/management and reuses `queryTransactionsAction` with visible + direction in + end_date today, page size 25 and optional account/private search. These are advisory filters; the confirmation endpoint independently verifies source ownership, effective visibility, positive amount, nonfuture date and expected transaction version. Any category, including an unconfirmed one, is eligible; selecting the receipt never changes its metadata. Missing/foreign source returns the same not_found. Owned but ineligible source returns `receipt_ineligible`; changed source returns version_conflict. Do not present the category name Salary as proof.

List and preview use admitted repeatable-read scopes with workspace timeouts; the sequence revision and interval/eligibility preview describe one snapshot. Cap preview/confirm/remove bodies at 16 KiB using measured read length, even without Content-Length. Validate singleton query parameters, positive bounded pagination offsets, versions and confirmation flags before data access beyond admission. A source lookup is always owned, even for an already-confirmed date.

For confirm/remove, use a short read-committed `CustomerDbScope` with exclusive customer admission and workspace timeouts. This serializes sequence edits before locking the source account/transaction, consistent with the existing customer → session → account → transaction order. Re-read the source under the locks used to prevent statement deletion/parent visibility and individual mutation racing eligibility. Do not hold a transaction between preview and user confirmation. Compare the sequence revision before any real effect; a stale sequence returns `409 cycle_sequence_changed` with no write and requires a new preview. A new date increments revision exactly once. An eligible same-date confirmation returns the existing date as already_confirmed without replacing anything or incrementing revision, even when its expected sequence revision is old; it has no effect. A stale source never bypasses source validation through that no-op path.

Deleting a boundary checks revision and owner; it increments sequence revision once. An explicit correction is remove, then select another receipt, with each affected range made visible; it is not an implicit replace operation. Removing an earliest date can make earlier transactions unavailable in salary mode; calendar/custom remain available. Adding a date inside a historical cycle splits it and may change later comparisons. Preview must describe this before confirmation, not only the newly added cycle. After a known success, refresh the complete current report and boundary list. After an uncertain response, read the sequence and show the observed date/revision; do not automatically repeat removal, manufacture success or change expected versions. A removed and later re-added date has a new ID; an old removal must not remove it.

Lifecycle: no boundaries → setup required → one confirmed start/open cycle → additional start closes its predecessor and opens a new latest cycle. Explicit earlier starts/removals recompute adjoining ranges. Source category/tag/hide/restore/delete changes never change confirmed dates, but do change included financial data. There is no monthly job, salary detector, automatic projection or boundary backfill.
